## 1. 目的与概念

定义 XS 领域标签的管理/检索语义，以及 repository/tag/kind 层级如何决定仓库的有效操作策略。XS 标签是 XS 自己的分类，不是 Git tag、branch 或 commit。

本 SPEC 只定义产品可观察的分类和策略结果；API route、数据库关系表、CLI 语法和 UI 控件由后续实现 PLAN 决定。

## 2. 参与者与入口

| 参与者 | 能力 | 入口类别 | 结果可见性 |
|---|---|---|---|
| 人类用户 | 创建/管理标签、筛选仓库、查看或设置仓库/标签策略、查看受影响仓库 | WebUI、CLI | 可视化呈现成员数量、策略来源和有效值 |
| Agent / 自动化 | 创建/管理标签、筛选仓库、查看或设置仓库/标签策略、查看受影响仓库 | CLI、HTTP API | 可解析取得相同能力的成员、策略来源和有效值 |
| 生命周期操作 | 执行 clone/pull/move 等仓库动作 | 复用操作服务 | 只读取 effective policy，不重新解释标签优先级 |

人类用户与 Agent 的标签/策略功能集合相同；入口只改变交互及结果呈现，对同一仓库必须返回一致的 effective policy。

对 Agent 发起的破坏性操作，本地人类操作者是确认主体；Agent 可提出待决策请求，但不能将自身请求当成确认。本产品范围不引入多用户审批层级。

## 3. 标签能力

| 能力 | 当前状态 | 契约状态 |
|---|---|---|
| XS 标签创建/列举/删除、仓库关联/解除 | 已实现 | 保留现有用户能力 |
| Repo/tag policy 设置和 repo 优先 | 已实现 | 明确有效来源和入口一致性 |
| 多 tag 策略生效顺序 | 部分实现 | 契约规则已冻结为 normalized slug 升序取首个有策略标签；实现补显式排序由后续实现 PLAN 承接 |
| 策略变更的成员影响预览 | 部分实现 | 显示受影响仓库和 effective policy 变化 |

- 操作者可以创建、列出、关联和解除仓库标签；标签可用于仓库过滤、聚合和策略范围。
- 创建标签时名称/slug 必须可辨识且可重复引用；重名输入不得静默创建两个难以区分的标签。slug 是标签的稳定唯一标识（见 `README.md` 术语表），同一 slug 重复输入指向同一标签。
- 删除或解除标签不改变 Git 仓库内容、remote、tag 或 commit。
- 搜索结果和仓库详情显示 XS 标签；标签仅作为分类，不隐含“冻结”“归档”或允许写入等含义。
- 新标签未附带策略时，不改变成员仓库当前有效操作行为。

## 4. 策略归属与优先级

策略用于约束操作：pull/update 的更新许可与冲突动作；move/备份等写操作的执行许可。允许的更新策略取值：`fetch-only`（只读取远端状态，不合并）、`mirror`（允许更新）、`no-update`（禁止更新）。允许的冲突动作取值：`stop`、`backup`、`overwrite`、`skip`。

默认优先级为：

1. 仓库级策略覆盖标签级策略。
2. 无仓库级策略时，从仓库已关联且配置了策略的标签中选出一个有效策略：按 normalized tag slug 升序，取首个配置了策略的标签（2026-09-30 用户批准冻结；实现需补显式排序后该顺序才成为可依赖的运行事实）。
3. 无适用标签策略时，使用仓库 kind 的默认策略。

多标签同时配置策略时，有效策略必须可重复计算、在查询结果中显示来源。现有 `USER-001-webui.md`（zh-Hans）记录按顺序 first-match；实现读取关联 tag IDs 时没有显式排序，故当前运行行为尚不能当作稳定实现事实，由后续实现 PLAN 补齐。修改标签或标签策略后，用户/Agent 可识别哪些仓库的生效策略因此变化。

有效策略至少区分：是否允许更新（取值见上）、交互式冲突动作、无人值守（unattended）冲突动作。`overwrite` 等破坏性结果必须有明确后果和用户授权，不得由标签隐式触发静默覆盖。

## 5. 主要流程

- 创建标签并关联一个或多个仓库；标签可用于后续查询与聚合。
- 给标签设置默认策略；未设置仓库级例外的成员仓库继承该策略。
- 为单个仓库设置策略例外；该值覆盖其所有标签策略。
- 检索/查看仓库时显示有效策略和来源（repo、具体 tag 或 kind default）。
- 策略变化后，新的仓库操作按新策略执行；正在执行的操作不被无声改写，具体取消/生效时点留给任务/操作契约定义。

## 6. 失败与安全边界

策略许可与单次人工确认是两个不同门：effective policy 决定操作是否允许及采用何种冲突动作；可能覆盖/丢失用户数据的单次操作还需要确认。无人值守策略只有在本地人类操作者预先设置后才构成该类 pull 冲突的持续授权，不代表 Agent 可自我确认。

| 操作类型 | 策略许可 | 人工确认 |
|---|---|---|
| 查询、搜索、只读状态 | 不适用写策略 | 不需要 |
| 按策略执行常规 pull/update | 必须允许更新 | 操作者明确请求或预先配置的无人值守（unattended）策略；不得超出策略 |
| 交互式 overwrite / backup 冲突决策 | 必须有适用冲突策略 | stop 转待决策；overwrite 的数据丢弃影响需本地操作者确认 |
| 独立备份 restore / prune | 必须是用户可执行的操作 | 每次需本地人类操作者确认；Agent 只能请求，不能自行确认 |

本产品范围不引入多用户/多层审批；本地人类操作者是确认主体。backup restore/prune 的具体数据语义由备份 SPEC 定义。

- 未知标签、未注册仓库或无效策略值必须明确拒绝，不得把错误输入解释为默认允许。
- 有效策略无法唯一解析时，不执行写操作；返回可诊断的策略来源和冲突原因。
- 标签策略变更不得修改仓库文件或 Git 元数据。
- 交互式与无人值守策略分别展示和审查；Agent 不得把自身请求冒充用户确认。
- 测试/生产策略和数据存储隔离；测试上下文不能更新生产 root。

## 7. 验收场景

| 编号 | 场景 | 操作 | 预期结果 |
|---|---|---|---|
| T1 | XS tag 与 Git tag 区分 | 给仓库添加名为 `release` 的 XS 标签 | 仓库可按 XS 标签筛选；Git refs 和仓库文件不变化 |
| T2 | 标签策略继承 | 给标签设置策略，成员仓库无 repo override | 成员仓库显示该标签为策略来源并应用对应操作规则 |
| T3 | 仓库级覆盖 | 给成员仓库设置独立策略 | repo policy 覆盖所有 tag policy，其他成员不受影响 |
| T4 | 多标签策略 | 仓库关联多个带策略标签 | 取首个有策略标签（normalized slug 升序），并显示来源；无法唯一确定时拒绝写操作 |
| T5 | 禁止更新 | effective policy 为 `no-update` | pull/update 在写入前拒绝（结果记为 `skipped`，拒绝语义）并说明策略来源 |
| T6 | 破坏性冲突动作 | 冲突策略选择 overwrite | 明示将丢弃的状态并取得对应确认；否则保持原仓库不变 |

## 8. 非目标与待确认

- 不定义 Git tag/branch/commit 的创建或删除。
- 多标签优先顺序契约已冻结（slug 升序）；当前实现未显式排序，运行行为不得当作稳定事实，排序补齐归后续实现 PLAN。
- 不冻结策略 JSON、数据库 schema、HTTP route 或 CLI 参数。
